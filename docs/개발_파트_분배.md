## 0. 이미 준비된 것 (develop 브랜치)

각 기능은 아래 기반 위에 만든다. 실행 방법과 사용법은 각 폴더의 README에 있다.

| 영역 | 준비된 것 | 안내 |
|---|---|---|
| 백엔드 | Spring Boot 4.0.8(Java 17) 프로젝트, 패키지 구조, `application.properties`, 공통 응답(`ApiResponse`·`PageResponse`), 에러 코드 전체와 전역 예외 처리, 엔티티·enum 전체, 임시 보안 설정, 임시 `SecurityUtil`, 확인용 `/api/health` | [`backend/README.md`](../backend/README.md) |
| 관리자 화면 | Thymeleaf 레이아웃 뼈대, 확인용 `/admin/preview`, `/admin/login` 뼈대 | [`backend/README.md`](../backend/README.md) |
| 프론트엔드 | Vite + React, Tailwind·shadcn 설정, 폴더 구조, 라우터(코드 스플리팅), 레이아웃, ProtectedRoute, 토큰 헤더를 붙이는 axios, authStore 뼈대, MSW Mock 연결, `devLogin()` | [`frontend/README.md`](../frontend/README.md) |
| Mock 데이터 | API별 정상·오류 응답 JSON, 테스트 계정 | [`mock-data/README.md`](../mock-data/README.md) |

**킥오프 때 각자 확인할 것**

1. `git checkout develop` → `git pull`
2. MariaDB에 `kdsq_db` 생성 + `boot` 계정 권한 부여 (backend README 1단계)
3. 백엔드 실행 → http://localhost:8080/api/health 응답 확인
4. 프론트 `npm install` → `npm run dev` → 콘솔 `devLogin()` 후 `/surveys/p` 접속 확인

## 1. 담당표

## 3. 프론트엔드 상세

프론트는 백엔드를 기다리지 않고 Mock 데이터(MSW)로 수요일까지 개발한 뒤, 목요일에 실제 API로 바꾼다. 로그인 화면이 완성되기 전에는 브라우저 콘솔의 `devLogin()`으로 테스트 로그인한다.

### 강찬식 — 인증 흐름 + 로그인·회원가입·마이페이지

프론트 공통 파일(`package.json`, `vite.config.js`, `App.jsx`, `axiosInstance`, `authStore`)의 주인이다.

- [ ] axios 응답 인터셉터: `ACCESS_TOKEN_EXPIRED` → 재발급 후 1회 재시도, 그 외 401 → 로그아웃. `/auth/login`·`/auth/reissue`·`/auth/logout` 요청의 401은 처리 제외 (React 5.3)
- [ ] authStore `login()`·`logout()`·`clear()`(다른 스토어의 `reset()` 호출), Header 로그인 상태별 메뉴·로그아웃·모바일 메뉴
- [ ] 로그인 상태로 `/login`에 들어오면 `/surveys/p`로 이동 (UI 3.1.5)
- [ ] LoginPage·LoginForm (401·403 문구)
- [ ] RegisterPage (입력 검증 4.2, `utils/validation.js`, 서버 `fields` 표시, 409는 이메일 입력칸 아래). 전송 시 `birthYear`는 숫자로, `passwordConfirm`은 제외 (React 5.2.2). 오류 문구는 REST 3.1.1 표 기준 (Mock `handlers.js` 문구도 같이 맞춤)
- [ ] MyPage: ProfileCard, ExamHistoryTable(10건씩), ExamTrendChart(Recharts, 5.5), EmptyHistory, WithdrawDialog, memberStore. 탈퇴 성공 후에는 `logout()` 대신 `clear()` (React 5.2.11). 이력 데이터는 `memberStore.fetchMyResults()`로 직접 조회 (React 4.3). 로딩·오류 상태는 1개씩, 이력 표 날짜는 `formatDateOnly()`(`utils/date.js`에 추가)
- [ ] 프론트 PR 검토·병합

- [ ] surveyStore(`surveyIdOf`, 설문 목록이 비면 다시 조회), resultStore(`pendingFirstAnswers` sessionStorage 유지). 두 스토어 모두 `reset()` 액션 포함 (React 4.3)

### 황지영 — 관리자 화면 (Thymeleaf)

템플릿은 백엔드 프로젝트의 `src/main/resources/templates`에 둔다 (UI 2.5 파일 구조). 이미 있는 레이아웃·로그인 뼈대를 설계서에 맞춰 완성한다.

- [ ] `layout/admin-layout.html` + 프래그먼트(header·sidebar·breadcrumb·flash·pagination·footer), `admin.css`, `admin.js`
    - 헤더의 관리자 이름은 `${adminName}`, 페이지 링크는 `${@pageUrl.to(i)}`, 검색어 강조는 `th:utext="${@highlight.mark(...)}"` (UI 2.5)
    - 검사 결과 목록의 보기 링크·삭제 폼, 상세의 목록 버튼·삭제 폼에 `returnUrl` 포함 (UI 2.5 "목록으로 돌아오기")
    - 사이드바 현재 메뉴는 `${currentPath}`로 판단 (`#request` 사용 불가). 날짜·검사 종류·판정 표기는 UI 2.5 "관리자 템플릿 공통 표기" 표 기준
- [ ] ADM-01 로그인(`?error`·`?logout` 상태)
- [ ] ADM-03 회원 목록(검색어 하이라이트), ADM-04 상세, ADM-04-1 수정 폼(`th:object`·`th:errors`) — 이원구 컨트롤러와 연결
- [ ] ADM-05 검사 결과 목록(필터 유지·하이라이트), ADM-06 상세(판정 기준 표시) — 이원구 컨트롤러와 연결

- [ ] 에러 페이지 403·404·500 (관리자 레이아웃 없이 단독 페이지, UI 2.5), 탈퇴·삭제는 POST 폼 + 확인창
- [ ] 관리자 화면이 완성되면 확인용 `admin/preview.html`과 `WebConfig`의 `/admin/preview`를 삭제

## 5. 파트 간 약속

### 5.1 파일 주인

여러 사람이 동시에 수정하면 충돌하는 파일은 주인을 한 명으로 정한다. 다른 사람은 수정이 필요하면 주인에게 요청한다.

| 담당 | 파일 |
|---|---|
| 윤수연 | `build.gradle`, `application.properties`, `ErrorCode`, `ApiResponse`, `SecurityConfig`, `SecurityUtil` |
| 이주혁 | `data.sql`, `SurveyRepository`, `QuestionRepository`, `SurveyResultRepository`, `SolutionRepository` |
| 강찬식 | `package.json`, `vite.config.js`, `App.jsx`(라우터), `axiosInstance`, `authStore` |

### 5.2 임시 인증

JWT가 완성되기 전까지 로그인한 회원 id는 `SecurityUtil.currentMemberId()`로만 얻는다 (지금은 항상 2). 서버를 처음 켜면 관리자 계정이 1번으로 자동 등록되므로, 테스트 전에 회원가입 API로 회원을 1명 만들어 2번 회원을 준비한다 (`backend/http/member.http`의 첫 요청). JWT가 완성되면 이 함수의 내부만 교체하므로, 이를 사용하는 다른 코드는 고칠 필요가 없다.

**개발용 샘플 데이터:** 관리자 목록·검색·대시보드처럼 데이터가 많아야 확인되는 화면은 `backend/http/sample-data.sql`(회원 27명·검사 결과 119건, Mock 데이터와 같은 내용)을 실행해서 모두 같은 데이터로 개발한다. 실행 방법은 파일 맨 위 주석에 있다. 비밀번호는 모두 `Test1234!`.

### 5.4 Git 규칙 (강사님 브랜치 전략)

- 작업 전 `git checkout develop` → `git pull`로 최신 상태를 받고, `develop`에서 `feature/be-…`, `feature/fe-…` 브랜치를 만든다.
- 작업이 끝나면 PR로 `develop`에 합친다. **PR을 만들 때 base가 `develop`인지 꼭 확인한다.** `main`은 10/5에만 병합한다.
- `main`, `develop`에는 직접 커밋하지 않는다. 설계서·문서도 마찬가지다.
- **설계서·문서의 최신본은 `develop` 기준이다.** 문서를 고칠 때는 `develop`에서 `docs/수정내용` 브랜치를 만들어 PR로 올린다. 기능 브랜치(`feature/*`)에서는 설계서를 고치지 않는다.
- PR 검토·병합: 백엔드 윤수연, 프론트엔드 강찬식
- 커밋 메시지: `타입: 요약` (`feat`, `fix`, `docs`, `refactor`, `test`, `chore`)
- 기능 하나·파일 묶음 하나 단위로 하루에 여러 번 커밋한다. 개별 평가가 커밋 기록을 기준으로 하므로 하루치 작업을 모아 한 번에 올리지 않는다.
- `application-local.properties`, `.env.development.local` 같은 개인 설정 파일은 올리지 않는다 (`.gitignore`에 등록됨).
- 매일 저녁 디스코드에 **오늘 한 일 / 내일 할 일 / 막힌 점**을 한 줄씩 남긴다.
