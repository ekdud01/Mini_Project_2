# 1. API 설계 개요

## 1.1 설계 목적
> KDSQ-P(1차) 및 KDSQ-C(2차) 인지선별검사, 회원 관리, 검사 결과 및 맞춤 솔루션 조회 기능을 RESTful API로 제공

## 1.2 설계 원칙
- **RESTful 아키텍처**: HTTP 메서드와 상태 코드의 올바른 사용
- **일관성**: 모든 API 엔드포인트에서 동일한 규칙 적용  
- **버전 관리**: URL 경로를 통한 버전 구분 
- **보안**: JWT 기반 인증
- **성능**: 검사 결과 및 이력 조회를 고려한 페이지네이션
- **문서화**: JSON 기반 요청/응답

## 1.3 기술 스택
- **Framework**: Spring Boot 4.0.8
- **인증**: JWT(JSON Web Token)
- **직렬화**: JSON
- **API 문서**: OpenAPI 3.0(Swagger)
- **DB**: MariaDB
- **ORM**: Spring Data JPA

## 1.4 리소스 설계 방향

검사 진행과 결과 관리의 성격이 다르므로 리소스를 `surveys`와 `results`로 분리한다.

| 리소스 | 책임 | 주요 API |
|--------|------|----------|
| `surveys` | 검사 문항 정의 및 조회 | `GET /api/surveys`, `GET /api/surveys/{surveyId}/questions` |
| `results` | 응답 제출, 채점, 위험도 판정, 결과·이력 조회, 솔루션 제공 | `POST /api/results`, `GET /api/results/{resultId}`, `GET /api/members/me/results` |

- 문항별 응답(answers)은 저장하지 않으므로 제출 시 생성되는 리소스는 결과뿐이다. 따라서 제출은 `POST /api/results`로 한다.
- 검사 1회당 결과는 1건만 저장한다. KDSQ-P 0\~3점이면 1차 제출 시 저장하고, 4점 이상이면 KDSQ-C 제출 시 1차 답변과 함께 제출하여 1건으로 저장한다. 2차 대상자가 중간 이탈하면 저장하지 않는다.
- 최종 채점·판정은 서버가 수행한다. 클라이언트의 1차 합계는 화면 이동 판단에만 사용한다.
- 관리자 기능은 Thymeleaf 서버 렌더링(`/admin/**`)으로 제공하므로 이 문서의 REST API 범위에 포함하지 않는다. (UI 화면설계서 4장 참고)

# 2. API 공통 규칙

## 2.1 URL 설계 규칙

| 규칙 | 설명 | 좋은 예 | 나쁜 예 |
|------|------|------|-------|
| **명사 사용** | 동사가 아닌 명사로 리소스를 표현 | `/api/members` | `/api/getMembers` |
| **복수형 사용** | 컬렉션은 복수형으로 표현 | `/api/surveys` | `/api/survey`| 
| **계층 구조** | 연관된 리소스 간의 관계를 URL로 표현 | `/api/members/me/results` | `/api/getMemberResults` |
| **소문자 사용** | URL은 소문자로 일관되게 표현 | `/api/members` | `/api/Members` |
| **동작 표현** | 생성·조회·수정·삭제 등의 동작은 HTTP 메서드로 구분 | `POST /api/members` | `/api/createMember` |


## 2.2 HTTP 메서드 사용 규칙 

| 메서드 | 용도 | 멱등성 | 안전성 | 예시 |
| ----- | ---- | ---- | ---- | ---- |
| **GET** | 리소스 조회 | ✅ | ✅ | `GET /api/surveys` |
| **POST** | 리소스 생성 및 검사 결과 제출 | ❌ | ❌ | `POST /api/results` |
| **PUT** | 리소스 전체 수정 | ✅ | ❌ | `PUT /api/{resources}/{id}` (현재 사용 API 없음) |
| **PATCH** | 리소스 부분 수정 및 상태 변경 | ❌ | ❌ | `PATCH /api/{resources}/{id}` (현재 사용 API 없음) |
| **DELETE** | 리소스 삭제 | ✅ | ❌ | `DELETE /api/members/me` (회원 탈퇴) |


## 2.3 HTTP 상태 코드 가이드 

| 코드 | 상태 | 설명 | 사용 예시 |
| ---- | ---- | ---- | ---- |
| **200** | OK | 요청 성공 (응답 데이터 포함) | GET 조회 성공 |
| **201** | Created | 리소스 생성 성공 | POST 요청 성공 (회원가입, 검사 결과 제출) |
| **204** | No Content | 요청 성공 (응답 데이터 없음) | DELETE 요청 성공 (회원 탈퇴), 로그아웃 |
| **400** | Bad Request | 잘못된 요청 | 필수값 누락 또는 요청값 검증 실패 |
| **401** | Unauthorized | 인증 필요 | 로그인하지 않았거나 토큰이 없거나 만료된 경우 |
| **403** | Forbidden | 접근 권한 없음 | 허용되지 않은 리소스 접근 |
| **404** | Not Found | 리소스를 찾을 수 없음 | 존재하지 않는 회원 또는 검사 결과 조회 |
| **409** | Conflict | 리소스 상태 충돌 | 이미 가입된 이메일로 회원가입 시도 |
| **422** | Unprocessable Entity | 비즈니스 규칙 위반 | 검사 결과의 점수 범위 또는 검사 진행 규칙 위반 |
| **500** | Internal Server Error | 서버 내부 오류 | 예기치 않은 서버 오류 |


## 2.4 공통 요청 헤더

```
Content-Type: application/json
Accept: application/json
Authorization: Bearer {JWT_TOKEN}
```

## 2.5 공통 응답 형식

모든 REST API 응답은 공통 응답 DTO `ApiResponse<T>`로 감싼다. 성공 시 `success`, `data`, `message`, `timestamp`를, 실패 시 `success`, `error`(`code`, `message`), `timestamp`를 담는다. 목록 응답은 `data` 안에 `content`와 `page`를 둔다. (단, 204 No Content 응답은 본문이 없다)

### 성공 응답 (단일 객체)

```json
{
  "success": true,
  "data": { /* 실제 데이터 */ },
  "message": "요청이 성공적으로 처리되었습니다",
  "timestamp": "2026-09-23T10:30:00Z"
}
```

### 성공 응답 (목록/페이지네이션)

```json
{
  "success": true,
  "data": {
    "content": [/* 데이터 배열 */],
    "page": {
      "number": 0,
      "size": 20,
      "totalElements": 100,
      "totalPages": 5,
      "first": true,
      "last": false
    }
  },
  "message": "목록 조회가 완료되었습니다",
  "timestamp": "2026-09-23T10:30:00Z"
}
```

### 에러 응답 

모든 에러 응답은 아래 형식으로 통일한다. `error.code`는 5장의 에러 코드를 사용하며, 클라이언트는 HTTP 상태 코드가 아니라 `error.code`로 분기한다.

```json
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "이메일 형식이 올바르지 않습니다"
  },
  "timestamp": "2026-09-23T10:30:00Z"
}
```

# 3. 인증 및 권한 관리 

## 3.1 JWT 토큰 기반 인증

### 3.1.1 회원가입 API

```yaml
POST /api/members
Content-Type: application/json
Public API (인증 불필요, permitAll)

Request Body:
{
  "email": "user@example.com",
  "password": "password123!",
  "name": "김철수",
  "gender": "MALE",
  "birthYear": 1955
}

Validation Rules:
- email: 필수, 이메일 형식, 최대 100자 (@NotBlank @Email @Size(max=100)), 중복 불가 (409 DUPLICATE_EMAIL)
- password: 필수, 공백 불가 (@NotBlank), BCrypt 암호화 저장
- name: 필수, 1~50자 (@NotBlank @Size(max=50))
- gender: 필수, MALE 또는 FEMALE (@NotNull)
- birthYear: 필수, 1900 ~ 현재연도 (@NotNull @Min(1900), 현재연도 초과 시 400 VALIDATION_ERROR)
- 검증 실패 시 400 VALIDATION_ERROR (필드별 오류 메시지 포함)
- 비밀번호 확인(passwordConfirm)은 화면에서만 검증하며 서버로 보내지 않음

Business Rules:
- 가입한 계정은 role = MEMBER, status = ACTIVE로 생성 (ADMIN 계정은 가입으로 만들 수 없음)

Response (201 Created):
{
  "success": true,
  "data": {
    "id": 1,
    "email": "user@example.com",
    "name": "김철수",
    "gender": "MALE",
    "birthYear": 1955,
    "status": "ACTIVE"
  },
  "message": "회원가입이 완료되었습니다"
}

Response (409 Conflict):
{
  "success": false,
  "error": {
    "code": "DUPLICATE_EMAIL",
    "message": "이미 사용 중인 이메일입니다"
  }
}
```

### 3.1.2 로그인 API

```yaml
POST /api/auth/login
Content-Type: application/json
Public API (인증 불필요, permitAll)

Request Body:
{
  "email": "user@example.com",
  "password": "password123!"
}

Response (200 OK):
{
  "success": true,
  "data": {
    "accessToken": "JWT_ACCESS_TOKEN",
    "refreshToken": "JWT_REFRESH_TOKEN",
    "tokenType": "Bearer",
    "expiresIn": 3600
  },
  "message": "로그인이 성공하였습니다"
}

Response (401 Unauthorized):
{
  "success": false,
  "error": {
    "code": "INVALID_CREDENTIALS",
    "message": "이메일 또는 비밀번호가 올바르지 않습니다"
  }
}

Response (403 Forbidden):
{
  "success": false,
  "error": {
    "code": "MEMBER_WITHDRAWN",
    "message": "이용할 수 없는 계정입니다"
  }
}
```

### 3.1.3 토큰 재발급 API

```yaml
POST /api/auth/reissue
Content-Type: application/json
Public API (액세스 토큰 만료 상태에서 호출)

Request Body:
{
  "refreshToken": "JWT_REFRESH_TOKEN"
}

Response (200 OK):
{
  "success": true,
  "data": {
    "accessToken": "NEW_JWT_ACCESS_TOKEN",
    "tokenType": "Bearer",
    "expiresIn": 3600
  }
}

Response (401 Unauthorized):
{
  "success": false,
  "error": {
    "code": "INVALID_REFRESH_TOKEN",
    "message": "다시 로그인해주세요"
  }
}

Business Rules:
- 리프레시 토큰이 만료·폐기·위조된 경우 INVALID_REFRESH_TOKEN (클라이언트는 재발급을 다시 시도하지 않고 로그아웃)
```

### 3.1.4 로그아웃 API

```yaml
POST /api/auth/logout
Authorization: Bearer {JWT_TOKEN}

Business Rules:
- 서버에 저장된 리프레시 토큰 폐기

Response (204 No Content)
```

## 3.2 권한 레벨 정의

| 역할 | 권한 | 비고 |
|------|------|------|
| **MEMBER** | 회원가입, 로그인, 본인 정보 조회, 본인 탈퇴, 설문 문항 조회, 검사 응시, 본인 검사 결과/이력 조회 | 일반 사용자. 회원정보는 가입 후 수정할 수 없음 (변경은 관리자에게 요청) |
| **ADMIN** | 회원/검사 결과 관리 및 대시보드 | 관리자 화면(회원 조회·수정·비활성화, 검사 결과 관리, 대시보드)은 Thymeleaf 서버 렌더링(`/admin/**`)으로 제공하며 REST API를 사용하지 않음 |

## 3.3 인증 방식 분리

사용자 화면(React)과 관리자 화면(Thymeleaf)은 인증 방식을 분리한다. Spring Security의 `SecurityFilterChain`을 URL 패턴별로 2개 구성한다.

| 구분 | URL 패턴 | 인증 방식 | 세션 | 권한 |
|------|----------|-----------|------|------|
| 사용자 API | `/api/**` | JWT (`Authorization: Bearer {토큰}`), 액세스·리프레시 토큰 | 사용 안 함 (STATELESS) | `ROLE_MEMBER` (Member.role = MEMBER). 회원가입·로그인·토큰 재발급만 `permitAll`. ADMIN 계정은 사용자 로그인 불가 (401 INVALID_CREDENTIALS) |
| 관리자 화면 | `/admin/**` | Spring Security `formLogin` (이메일·비밀번호, 초기 데이터로 사전 등록된 관리자 계정) | 세션 기반 | `ROLE_ADMIN` (Member.role = ADMIN). `/admin/login`만 `permitAll`, CSRF 토큰 적용. MEMBER 계정은 관리자 로그인 불가 |

- 비밀번호는 사용자·관리자 모두 BCrypt로 암호화하여 저장한다.
- 본인 데이터 접근(`/api/members/me/**`, `/api/results/{resultId}`)은 토큰의 회원 id로 소유자를 확인한다.
- 사용자·관리자 계정은 모두 Member 엔티티에 저장하고 `role`(MEMBER/ADMIN)로 구분한다. 관리자 계정은 회원가입으로 만들 수 없으며 애플리케이션 시작 시 초기 데이터로 등록한다. (Entity 설계서 12장)

**토큰 오류 처리 규칙**

| 상황 | 에러 코드 | 클라이언트 처리 |
|------|-----------|-----------------|
| 액세스 토큰 만료 | 401 `ACCESS_TOKEN_EXPIRED` | `POST /api/auth/reissue`로 재발급 후 원래 요청 1회 재시도 |
| 리프레시 토큰 만료·폐기·위조 | 401 `INVALID_REFRESH_TOKEN` | 재발급을 다시 시도하지 않고 로그아웃 → `/login` |
| 토큰 없음·위조된 액세스 토큰 | 401 `UNAUTHORIZED` | 로그아웃 → `/login` |

# 4. 상세 API 명세

## 4.1 회원 관리 API

### 4.1.1 내 정보 조회

```yaml
GET /api/members/me
Authorization: Bearer {JWT_TOKEN}
Required Role: MEMBER

Response (200 OK):
{
  "success": true,
  "data": {
    "id": 1,
    "email": "user@example.com",
    "name": "김철수",
    "gender": "MALE",
    "birthYear": 1955,
    "status": "ACTIVE",
    "createdAt": "2026-09-24T10:00:00Z"
  }
}
```

### 4.1.2 회원 탈퇴

```yaml
DELETE /api/members/me
Authorization: Bearer {JWT_TOKEN}
Required Role: MEMBER

Business Rules:
- 로그인한 회원 본인만 탈퇴 가능 (URL에 회원 id를 받지 않으므로 다른 회원 탈퇴 불가)
- 클라이언트 관점에서는 회원 리소스 삭제이며, 서버는 검사 이력 보존을 위해 물리 삭제하지 않고 상태만 ACTIVE → WITHDRAWN으로 변경 (소프트 삭제)
- 탈퇴와 함께 서버에 저장된 리프레시 토큰 폐기
- WITHDRAWN 회원은 재로그인 불가 (로그인 시 403 MEMBER_WITHDRAWN)
- 탈퇴 회원의 검사 결과는 삭제하지 않고 보존 (관리자 통계에 반영)

Response (204 No Content)

Response (404 Not Found):
{
  "success": false,
  "error": {
```

## 4.3 결과(results) API

**문항별 점수 체계**: 모든 문항은 3개 선택지 중 하나를 고르며, 선택지별 점수는 아래와 같다. 이에 따라 KDSQ-P는 5문항 × 최대 2점 = 10점 만점, KDSQ-C는 15문항 × 최대 2점 = 30점 만점(영역별 5문항 × 2점 = 10점 만점)이다.

| 선택지 | 점수 |
|--------|------|
| 전혀 그렇지 않다 | 0 |
| 가끔 그렇다 | 1 |
| 자주 그렇다 | 2 |

### 4.3.1 검사 결과 제출 — KDSQ-P에서 종료 (0~3점)

```yaml
POST /api/results
Content-Type: application/json
Authorization: Bearer {JWT_TOKEN}
Required Role: MEMBER

Request Body:
{
  "surveyId": 1,
  "answers": [
    { "questionId": 1, "score": 0 },
    { "questionId": 2, "score": 1 },
    { "questionId": 3, "score": 0 },
    { "questionId": 4, "score": 1 },
    { "questionId": 5, "score": 0 }
  ]
}

Validation Rules:
- surveyId: 필수, KDSQ-P 설문 ID
- answers: 필수, 정확히 5개 (아니면 400 INVALID_ANSWER_COUNT)
- answers[].questionId: 필수, 해당 설문의 문항 ID (아니면 404 QUESTION_NOT_FOUND)
- answers[].score: 필수, 0~2 정수 (@NotNull @Min(0) @Max(2), 아니면 400 VALIDATION_ERROR)

Business Rules:
- KDSQ-P는 5문항 검사
- 서버가 점수를 합산하여 firstScore 산출
- 0~3점: Normal 판정 후 결과 1건 저장
- 4~10점이면 저장하지 않고 422 KDSQ_C_REQUIRED 반환 (KDSQ-C 제출 시 함께 저장해야 함)
- 클라이언트는 5문항 합계가 0~3점일 때만 이 요청을 보낸다

Response (201 Created):
Location: /api/results/101
{
  "success": true,
  "data": {
    "id": 101,
    "examType": "KDSQ_P",
    "firstScore": 2,
    "memoryScore": null,
    "otherScore": null,
    "adlScore": null,
    "totalScore": null,
    "riskLevel": "Normal",
    "createdAt": "2026-09-24T10:30:00Z"
  },
  "message": "검사가 완료되었습니다"
}
```

### 4.3.2 검사 결과 제출 — KDSQ-C까지 완료 (1차 4~10점)

```yaml
POST /api/results
Content-Type: application/json
Authorization: Bearer {JWT_TOKEN}
Required Role: MEMBER

Request Body:
{
  "surveyId": 2,
  "firstAnswers": [
    { "questionId": 1, "score": 1 },
    { "questionId": 2, "score": 1 },
    { "questionId": 3, "score": 1 },
    { "questionId": 4, "score": 1 },
    { "questionId": 5, "score": 1 }
  ],
  "answers": [
    { "questionId": 6, "score": 1 }
    // ... KDSQ-C 15문항
  ]
}

Validation Rules:
- surveyId: 필수, KDSQ-C 설문 ID
- firstAnswers: 필수, 정확히 5개 (KDSQ-P 문항), answers: 필수, 정확히 15개 (KDSQ-C 문항)
  (개수가 다르면 400 INVALID_ANSWER_COUNT)
- questionId: 필수, 각 설문의 문항 ID (아니면 404 QUESTION_NOT_FOUND)
- score: 필수, 0~2 정수 (@NotNull @Min(0) @Max(2), 아니면 400 VALIDATION_ERROR)

Business Rules:
- KDSQ-C는 15문항 검사
- firstAnswers(KDSQ-P 5문항)를 서버가 다시 채점하여 4점 이상인지 검증
  (4점 미만이면 422 KDSQ_C_NOT_ALLOWED)
- 1~5번: memoryScore
- 6~10번: otherScore
- 11~15번: adlScore
- 총점 0~5점: Borderline
- 총점 6~30점: HighRisk
- 1차 점수(firstScore)와 영역별 점수를 합쳐 결과 1건 저장
- 2차 대상자가 KDSQ-C를 제출하지 않으면(중간 이탈) 결과는 저장되지 않음

Response (201 Created):
Location: /api/results/102
{
  "success": true,
  "data": {
    "id": 102,
    "examType": "KDSQ_C",
    "firstScore": 5,
    "memoryScore": 2,
    "otherScore": 2,
    "adlScore": 3,
    "totalScore": 7,
    "riskLevel": "HighRisk",
    "createdAt": "2026-09-24T10:35:00Z"
  },
  "message": "검사가 완료되었습니다"
}
```

# 5. 에러 코드 및 처리

## 5.1 표준 에러 코드 정의

| 코드 | HTTP 상태 | 설명 |
|------|-----------|------|
| **VALIDATION_ERROR** | 400 | 입력값 검증 실패 |
| **INVALID_CREDENTIALS** | 401 | 이메일 또는 비밀번호 오류 |
| **UNAUTHORIZED** | 401 | 토큰 없음 또는 위조된 토큰 |
| **ACCESS_TOKEN_EXPIRED** | 401 | 액세스 토큰 만료 (재발급 대상) |
| **INVALID_REFRESH_TOKEN** | 401 | 리프레시 토큰 만료·폐기·위조 (재로그인 필요) |
| **ACCESS_DENIED** | 403 | 접근 권한 없음 |
| **RESOURCE_NOT_FOUND** | 404 | 요청 리소스 없음 |
| **DUPLICATE_EMAIL** | 409 | 이미 사용 중인 이메일 |
| **BUSINESS_RULE_VIOLATION** | 422 | 비즈니스 규칙 위반 |
| **INTERNAL_SERVER_ERROR** | 500 | 서버 내부 오류 |

## 5.2 도메인별 에러 코드

| 코드 | HTTP 상태 | 설명 |
|------|-----------|------|
| **MEMBER_NOT_FOUND** | 404 | 회원을 찾을 수 없음 |
| **MEMBER_WITHDRAWN** | 403 | 탈퇴 회원 |
| **SURVEY_NOT_FOUND** | 404 | 설문지를 찾을 수 없음 |
| **QUESTION_NOT_FOUND** | 404 | 문항을 찾을 수 없음 |
| **RESULT_NOT_FOUND** | 404 | 검사 결과를 찾을 수 없음 |
| **INVALID_EXAM_TYPE** | 400 | 지원하지 않는 검사 유형 |
| **INVALID_ANSWER_COUNT** | 400 | 문항 수가 검사 유형과 일치하지 않음 (`answers`, `firstAnswers` 모두 검사) |
| **KDSQ_C_REQUIRED** | 422 | KDSQ-P 4점 이상인데 KDSQ-P 결과만 저장하려 함 |
| **KDSQ_C_NOT_ALLOWED** | 422 | 함께 제출된 KDSQ-P 답변이 4점 미만인데 KDSQ-C 결과를 저장하려 함 |

## 5.3 에러 처리 구현

- 에러 코드는 `ErrorCode` enum(코드, HTTP 상태, 기본 메시지)으로 관리한다.
- 비즈니스 예외는 `BusinessException(ErrorCode)`로 던지고, `@RestControllerAdvice` 전역 예외 처리기에서 2.5의 에러 응답 형식으로 변환한다.
- Bean Validation 실패(`MethodArgumentNotValidException`)는 `VALIDATION_ERROR`로 변환한다.

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(BusinessException.class)
    public ResponseEntity<ErrorResponse> handleBusiness(BusinessException e) {
        ErrorCode code = e.getErrorCode();
        return ResponseEntity.status(code.getStatus()).body(ErrorResponse.of(code));
    }
}
```

# 8. 마무리

## 8.1 주요 포인트 요약

1. **회원 관리**: 이메일 기반 회원가입/로그인, 내 정보 조회, 본인 탈퇴(소프트 삭제). 회원정보 수정은 관리자 화면에서만 가능
2. **설문(surveys)**: KDSQ-P 5문항, KDSQ-C 15문항 문항 조회
3. **결과(results)**: 답변 제출 → 서버 채점·위험도 판정, 검사 1회당 결과 1건 저장, 결과·이력 조회
4. **솔루션 제공**: Borderline/HighRisk 결과 상세에 솔루션 포함
5. **검사 이력 및 추이 제공**: 이력 API(4.3.4) 하나로 마이페이지의 검사 이력 목록과 시계열 추이 그래프를 함께 제공 (전체 사용자 통계는 관리자 대시보드에서 제공)
6. **인증/보안**: 사용자 API는 JWT, 관리자 화면은 formLogin(세션)으로 인증을 분리하고 본인/관리자 접근 제어
